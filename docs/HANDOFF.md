## Правила публичных текстов (обязательны с 12.11.2026)

1. **Для неограниченного круга читателей только уважительное обращение на «вы».** Никакого «ты», «тебе», «твой», «расскажи», «опиши», «запускаешь», «обновляешь» и других фамильярных форм. Исключение возможно только при специально согласованной авторской манере. При правках проверять **всю страницу**, включая заголовки, кнопки, форму, FAQ и текст в Schema.org.
2. **Описания кейсов от лица агентства:** «мы разработали», «мы обновили», «наш проект» вместо обезличенных «разработаны», «показана» и третьего лица «Heads сделало». Факты и реальный объем работ не расширять.
3. **Запрет переносить внутреннюю редакторскую кухню в клиентскую страницу.** Списки исключенных кейсов, ограничения публикации, проверки фактов, договоренности с представителями Heads, ограничения редактора и формулировки вроде «этот кейс не выдается за…» остаются исключительно в рабочих документах. На сайте рассказываем о выполненной работе, ее задаче и результате. При обнаружении подобного текста исправлять самостоятельно до публикации.
4. Новая вводная строка для страницы услуг — «Heads · Москва, Россия». Завершающий призыв: «Давайте обсудим задачу?». Обращение на «вы» используется и в коммерческих переходах.
5. Автоматическая проверка `scripts/check-geo.mjs` теперь запрещает фамильярные формы, внутренние ремарки в видимом тексте и требует подачи всех четырех кейсов от «мы». При добавлении нового блока расширять проверку.

## Следующий шаг при новом поручении

Если пользователь просит еще правки, работать с `main`, менять только нужные фрагменты, фиксировать коммит и проверять GitHub Actions. Если просит перенос на рабочий сайт, использовать канонические компоненты и WordPress/Yoast на действующем `/services/`, не загружать локальный `index.html` вместо всего сайта, не создавать дублей Schema.org и обязательно проверить публичную страницу на десктопе/мобиле.

## Согласование текстов Heads через Google-таблицу (12.11.2026)

**Единая рабочая таблица:** https://docs.google.com/spreadsheets/d/148dBU1gL_J9i9e8cYgVAYiVV8Hz8avNrKDxSfmMg1tY/edit

4 листа: «Услуги и полный цикл брендинга», «Стратегия и позиционирование», «Формирование портфеля брендов», «Дизайн упаковки». На данный момент заполнен только первый лист: **165 строк** (161 редакционное поле + 4 SEO-поля), остальные листы подготовлены с такими же колонками и пока без текстов.

Колонки: A постоянный ID, B раздел, C тип поля, D текущий точный текст, E новый текст Аллы, F комментарий Аллы, G технический адрес, H замечания (ссылки, жирное выделение, FAQ/разметка). Данные для Аллы находятся в **E5:E169**, пустые значения означают отсутствие изменений. Сначала считать данные таблицы, применять только непустые изменения E; не изменять ID и исходную колонку D.

В `index.html` теперь на 161 редактируемом текстовом элементе стоит `data-heads-text-id="HEADS-S01-0001"` ... `HEADS-S01-0161`. Дополнительные SEO-поля используют ID `HEADS-S01-SEO-01` ... `SEO-04` и селекторы `title`, `meta[name="description"]`, `meta[property="og:title"]`, `meta[property="og:description"]`. Каноническая карта: `docs/text-fields-services.json`. ID после согласования не перенумеровывать. При обновлении сохранять действующие HTML-ссылки, выделения, атрибуты и события форм; FAQ синхронизировать с FAQPage JSON-LD, а затем запускать `check-preview.mjs`, `check-geo.mjs`, `check-browser.mjs` и проверку live GitHub Pages. Общие шапка и подвал не включены в первую ведомость, поскольку они повторяются на всех страницах.

## Обязательная очистка служебных ID при переносе на рабочий сайт (решение от 12.11.2026)

**КАТЕГОРИЧЕСКОЕ ПРАВИЛО РЕЛИЗА:** `HEADS-S01-0001` … `HEADS-S01-0161` — внутренние идентификаторы временной таблицы согласования Аллы; они **не должны оставаться в коде финальной публичной страницы на wellhead.ru**. Это относится ко всем атрибутам вида `data-heads-text-id="HEADS-S01-..."`, а при переносе остальных 3 страниц — и к `HEADS-S02-...`, `HEADS-S03-...`, `HEADS-S04-...`, если такие ID будут введены.

Порядок: (1) сохранить ID только в копии GitHub и в таблице, пока продолжается согласование; (2) после утверждения применять все непустые правки Аллы по ID и синхронизировать FAQ/Schema.org; (3) **перед публикацией на WordPress удалить служебные атрибуты и любые внутренние метки согласования из итогового HTML**, сохранив штатные HTML-`id` элементов, классы, содержимое, ссылки, визуальное форматирование и функциональность; (4) открыть исходный код и DOM **живого** сайта после переноса и проверить отсутствие строк `HEADS-S01-`, `HEADS-S02-`, `HEADS-S03-`, `HEADS-S04-`, `data-heads-text-id`. Только после этого принимать перенос как завершенный. Не удалять идентификаторы преждевременно из GitHub-превью, иначе потеряется надежная связь с Google-таблицей.

**Правка внешнего вида:** в синем завершающем CTA на странице S01 перед «Мы уточним вводные, этапы и состав предложения.» установлен явный перенос строки (`<br>`) внутри текстового поля `HEADS-S01-0137`. На рабочей странице сохранить этот перенос, но удалить служебный `data-heads-text-id`.

## Единая цветовая разметка Google-таблицы Аллы (13.11.2026)

**Документ:** https://docs.google.com/spreadsheets/d/148dBU1gL_J9i9e8cYgVAYiVV8Hz8avNrKDxSfmMg1tY/edit. Во всех четырех листах строки **A:H** окрашены по происхождению текстового элемента:

- Бледно-голубой фон (примерно `#EAF3FB`) — только **впервые добавленные нами HTML-элементы/тексты**.
- Белый фон (`#FFFFFF`) — тексты и поля, существовавшие на исходном wellhead.ru, **даже если мы изменили их формулировки и метаописания**.
- Четыре строки заголовка/инструкции каждого листа сохраняют прежнее оформление; для новых строк наследовать стиль полей, затем применять цвет ко всей A:H. Столбец E — новая редакция Аллы, F — комментарий; пустая E = без изменений.

**Классификация на 13.11.2026:** S01 — 91 новый / 74 исходных (новые разделы 01, 03–07); S02 — 30 новых / 92 исходных (новые разделы 02–04); S03 — 47 новых / 97 исходных (`text-fields.json: kind=geo`, ID `HEADS-S03-0094...0140`); S04 — 67 новых / 106 исходных (`kind=geo`, ID `HEADS-S04-0103...0169`). Всего 235 добавленных и 369 исходных строк. При будущих правках классифицировать по фактическому происхождению элемента/сохраненным ID, а не по номеру строки: новые строки могут вставляться перед старыми. Существующие ID, заметки и правки Аллы сохранять.
